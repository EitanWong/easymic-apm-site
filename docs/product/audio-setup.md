# 设备与声音配置

APM 的效果来自算法与正确接入共同作用。建议先验证普通 AEC、ANS、AGC，再按项目需要加入阵列定向能力。

## 普通麦克风也能接入

基础 AEC、ANS、AGC 由软件算法提供，不要求复杂阵列硬件。选择稳定的输入设备，避免采集过载和削波，合理摆放麦克风与扬声器。

如果具备独立同步的阵列输入，可以进一步探索空间处理。不能只依据设备外观上的麦克风数量判断系统实际提供的通道。

## AEC：确认播放参考完整

麦克风听到的扬声器声音，必须在 AEC 的参考链路中有对应信号。在 Unity 中，请将需要被抵消的应用播放通过 EasyMic 播放链路送出。

常见问题包括：

- 系统或其他引擎播放了声音，却没有进入 EasyMic 参考。
- 将不相关的游戏音频总线当作实际扬声器输出。
- 播放参考过期、以突发方式提交或帧节奏不稳定。
- 切换音频设备后，仍使用旧的路由与延迟状态。

只应提交真实测得的宿主缓冲延迟，不要用通用猜测代替设备时序。

## ANS：先处理输入质量

背景降噪可减轻环境噪声，但不能恢复已经削波的录音，也不能保证移除与目标同方向、同时发生的其他讲话。请避免麦克风过载，并在实际场地调整设备摆放与参数。

## AGC：关注音量与距离变化

验证近距离、正常距离与较远距离的说话，观察听感是否稳定。同时检查设备自身的自动增益是否叠加；多层预处理可能影响最终体验。

## Android 与路由

Android 的外放、听筒、有线耳机和蓝牙使用不同的音频路由。宿主负责实际路由和音频模式，并向 APM 报告当前状态。

不要在没有明确策略的情况下同时启用硬件 AEC 与软件 AEC。设备“支持硬件 AEC”并不表示当前采集 session 已附着并启用它。

## 建议验证顺序

1. 确认安装、授权和麦克风权限。
2. 安静环境采集，检查输入是否失真或过载。
3. 播放但不说话，检查回声处理。
4. 同时播放与说话，检查自己的语音是否清楚。
5. 加入真实背景噪声，检查噪声抑制和音量变化。
6. 切换路由、暂停恢复，并测试最终构建。

这些检查用于帮助接入和排查，不能替代你的目标场地验收。
